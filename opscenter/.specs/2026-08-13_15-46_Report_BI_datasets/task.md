Status: In Progress

使用者已安排開始實作。資料庫 schema 與 migration 仍須依各工作項目的需要另行驗證，不得直接套用未確認的資料庫異動。

## 5. BI 資料集效能與彙總來源

- [x] 5.1 建立資料集查詢基準與慢查詢量測
  - 量測不同資料量、日期區間、篩選器與主專案範圍的原始 query
  - 記錄資料量、P50／P95、執行計畫與可接受的新鮮度
  - _Requirements: 效能與彙總來源策略_
  - 已完成：`cmd/benchmark_report` 的兩輪本機量測已記錄四個資料集、近 31 天／12 個月、人員口徑、篩選器與多主專案範圍的 P50／P95；第三輪已補 Ticket 與活動統計的實際 `EXPLAIN ANALYZE`。

- [x] 5.2 檢查並補齊原始資料表索引
  - 優先處理 `tickets` 的專案、建立時間及常用篩選／關聯欄位
  - 以 `EXPLAIN ANALYZE` 驗證索引實際被使用，不依名稱推測效能
  - _Requirements: 效能與彙總來源策略_
  - 已完成：Ticket 查詢在資料量較大的分區使用 `project_id + created_at`／`project_id + status + created_at` 索引；八月小分區僅 60 筆資料的 sequential scan 成本低。活動統計在 6,135 筆資料下約 13ms，無索引缺口證據，第一階段不新增索引。

- [x] 5.3 為已證實高頻且固定粒度的資料集設計彙總來源
  - 評估一般 view、materialized view 與預聚合表
  - `ticket_events` 維持原始查詢優先；值班、人員工作量與主專案月度彙總依量測決定
  - _Requirements: 效能與彙總來源策略；Design: 效能與實體來源_
  - 已完成：量測與執行計畫未顯示慢查詢或高頻固定粒度彙總需求；四個資料集維持原始 query planner。一般 view 不作為效能方案，未引入 materialized view 或預聚合表。

- [x] 5.4 設計刷新、資料新鮮度與失敗處理
  - 定義刷新時機、最大資料延遲、並行與失敗重試策略
  - payload 顯示 `refreshed_at` 與過舊／失敗狀態，不得靜默提供過期數字
  - _Requirements: 效能與彙總來源策略_
  - 已完成：第一階段由原始資料即時查詢，資料新鮮度為查詢當下，無 refresh job 或過期資料狀態；未來彙總來源的刷新、警示與重試契約已記錄於效能文件。

- [x] 5.5 驗證原始與彙總來源的口徑一致性
  - 對相同專案、日期、篩選器及指標比較結果
  - 覆蓋固定 OP 指標、零值、日期邊界、刪除資料、停用／封存專案及權限範圍
  - _Requirements: 指標治理、效能與彙總來源策略_
  - 已完成：第一階段沒有彙總來源，所有呈現直接使用既有原始 query planner；Report 測試驗證固定 OP 指標、零值、日期範圍、停用／封存主專案與權限範圍。未來新增彙總來源時必須依效能文件重新執行原始／彙總比對。

- [x] 5.6 建立 migration、部署、權限與回滾程序
  - 新增且只新增 migration，不修改已執行 migration
  - 刷新 job 使用受控部署流程；回滾先切回原始 query planner
  - _Requirements: 效能與彙總來源策略；Design: 效能與實體來源_
  - 已完成：第一階段不新增 schema、索引或 refresh job，因此不新增資料庫 migration；已在效能文件定義未來彙總來源的版本化 migration、單次受控部署 job、最小權限、刷新失敗警示與切回原始 query planner 的回滾程序。
