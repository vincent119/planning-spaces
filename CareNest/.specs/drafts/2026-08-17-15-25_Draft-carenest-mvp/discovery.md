## 主要使用者與情境

主要使用者是與長輩同住的家人。使用者通常在早餐、午餐、晚餐、補充營養、服藥與睡前等短暫空檔處理照護事項，沒有條件填寫冗長表單。

典型的一天：

1. 早上查看首頁，確認早餐與高蛋白補充。
2. 協助進食後，以一個動作記錄食用比例；需要交接時才附加相片或備註。
3. 發現長輩喝水後，從首頁累加對應水量。
4. 晚上確認未完成清單，處理晚餐與補充品。
5. 每週回顧七天資料，理解哪些照護目標經常未完成。

## 核心產品原則

1. 照護確認優先於資料完整性。每項常用紀錄先有最快路徑，細節輸入必須是選擇性的。
2. 使用者可調整照護計畫。產品不得暗示所有長輩需要相同的飲食、飲水或用藥目標。
3. 完成度是任務進度，不是健康分數。介面必須顯示組成項目與計算依據。
4. 健康資料最小化。只蒐集完成產品功能所需資料，預設只存於裝置。
5. 醫療邊界明確。所有趨勢描述為紀錄事實，避免「正常」、「危險」、「應該」等臨床性措辭。

## 每日完成度規則

### 計算單位

每日照護計畫由啟用項目組成，每個項目有權重與完成條件。預設所有啟用項目權重相同，使用者可在後續版本調整；MVP 不開放權重設定，以降低設定成本。

```
完成度 = 已完成啟用項目數 / 當日應執行啟用項目數 × 100
```

### 範例

早餐、午餐、晚餐、飲水、高蛋白共五項。若已完成早餐、午餐、飲水與高蛋白，完成度為 4 / 5，即 80%。

### 特殊規則

- 未啟用的項目不計入分母。
- 未安排的體重或血壓紀錄日不計入分母。
- 新增或調整計畫只影響調整後的日期；歷史完成度依當日的計畫快照保留。
- 完成度顯示整數百分比，同時顯示分子與分母，避免百分比造成誤解。

## 最小資料模型

| 實體 | 必要欄位 | 說明 |
| --- | --- | --- |
| CareRecipient | id、名稱、時區、建立時間 | 被照顧者主檔；預留多位支援，不在 MVP 介面開放 |
| CarePlan | id、recipientId、生效日、每日開始時間 | 每日照護目標的版本化容器 |
| CarePlanItem | id、planId、類型、啟用、目標、時段 | 決定完成度的項目設定 |
| MealRecord | id、日期、餐別、食用比例、照片路徑、備註、建立時間 | 相片只存本機沙盒 |
| SupplementRecord | id、日期時間、品項、份數、熱量、蛋白質、備註 | 營養數值以使用者輸入的品項資料為準 |
| WaterRecord | id、日期時間、ml | 一筆代表一次累加 |
| WeightRecord | id、日期時間、kg、備註 | 純紀錄，不判讀 |
| BloodPressureRecord | id、日期時間、收縮壓、舒張壓、脈搏、備註 | 純紀錄，不判讀 |
| CompletionSnapshot | 日期、planId、分子、分母、百分比 | 快取或可重建；必須保留當日計畫版本 |

## 體驗與提醒規則

- 首頁只顯示現在仍可處理或即將到期的當日項目，完整資料進入詳情頁查看。
- 使用者可為餐次、高蛋白補充或每日摘要設定提醒；初始設定不得預先要求開啟通知權限。
- 在使用者確定照護時段後，才請求通知權限，並說明用途。
- 未完成提醒使用中性語句，例如「晚間用藥尚未確認」，不使用帶有責備意味的內容。
- 相片一律可選，且在首次附加前說明僅儲存於裝置與備份中。

## 風險與處理

| 風險 | 影響 | 處理方式 |
| --- | --- | --- |
| 使用者誤解完成度為健康評分 | 可能延誤專業醫療諮詢 | 使用「照護事項完成度」完整名稱，列出明細，避免健康語彙 |
| 目標設定不適合個人 | 完成度失真，甚至造成危險建議 | 不提供預設醫療建議；首次設定說明依醫療團隊或家庭計畫自行填寫 |
| 紀錄流程過重 | 留存率低 | 常用動作一鍵化；照片、備註與數值細節皆為選填 |
| 換機或遺失資料 | 信任受損 | MVP 設計可還原的本機備份與明確復原流程 |
| 醫療資料隱私 | 資料暴露風險 | 本機存放、最小權限、備份加密、避免分析服務 |
