# Flutter 專案協作規範

## 目的

本文件供在 Flutter 專案中協作的代理使用。使用者目前仍在熟悉 Flutter，因此工作重點是建立可理解、可執行、可驗證的程式碼；避免在需求尚小時引入複雜架構或大量套件。

## 語言與溝通

- 預設以繁體中文（台灣用語）回應、撰寫文件、程式碼註解、日誌說明與提交訊息。
- 程式語言關鍵字、Flutter 元件、套件名稱、檔名與必要技術術語可保留英文。
- 先說明完成結果，再用簡短文字說明重要決策、影響範圍、驗證方式與尚未確認的風險。
- 資訊不足時，明確寫出「假設」與缺少的資訊；不得自行捏造需求或資料。
- 不使用 emoji，不以破折號作為強調手段。

## 開始工作前

1. 先閱讀專案根目錄的 `README.md`、`pubspec.yaml`、本文件，以及與需求直接相關的程式碼與測試。
2. 先以 `rg --files` 與 `rg` 定位檔案；不要一次掃描大量無關目錄、產物或相依套件快取。
3. 先檢查工作目錄狀態。既有未提交變更屬於使用者，除非需求明確涵蓋，否則不可覆寫、還原或格式化無關檔案。
4. 確認現有的狀態管理、路由、資料儲存、主題與測試慣例後，才決定如何修改。
5. 若專案尚未建立或需求只要求規劃，不得自行建立完整 Flutter 專案、引入套件或實作畫面。

## 私有規格工作區

- 所有產品規劃、需求、設計、任務與其他 SDD 文件，必須存放於 `$PRIVATE_SPEC_WORKSPACE/<repository>/.specs/`。
- `<repository>` 必須使用目前 Git repository 的目錄名稱；不可猜測其他專案名稱或跨專案共用規格目錄。
- 不得在程式 repository 內建立、修改或提交 `.specs/`，除非使用者明確覆寫此規則。
- 處理實作需求前，先讀取與本次需求直接相關的私有規格；不要掃描整個私有規格工作區。
- 若 `$PRIVATE_SPEC_WORKSPACE` 未設定、無法讀取，或目標 repository 無法判定，先回報原因並要求使用者指示；不可自行改將規格寫入程式 repository。
- 私有規格工作區的檔案仍需遵守最小修改原則，不得覆寫其他產品或其他需求的規劃內容。

## 開發原則

- 優先使用 Flutter 與 Dart 標準能力；新增第三方套件前，先確認現有相依是否已能解決問題。
- 新增套件必須說明用途、替代方案、維護狀態與對專案的影響，並由使用者確認是否需要時才加入。
- 先完成最小可用流程，再在明確需求下抽取共用元件、服務或抽象層。
- 不為未發生的需求預先建立 Repository、Service、UseCase、泛型基底類別或多層目錄。
- 保持單向資料流：畫面接收狀態、使用者動作呼叫明確事件、狀態更新後重建需要的畫面。
- 所有非同步工作必須處理載入、成功、失敗與取消或畫面銷毀情境。
- 不在 `build` 中執行網路請求、寫入資料、建立長期訂閱或改變狀態。
- 不將 `BuildContext` 跨非同步間隔不加檢查地使用；需要時確認 `context.mounted`。
- 不以 `dynamic`、強制轉型或忽略分析警告來繞過型別問題。

## 建議的漸進式結構

在功能仍少時，先採容易閱讀的結構，依功能成長再拆分：

```text
lib/
  main.dart
  app.dart
  features/
    <功能名稱>/
      <功能名稱>_page.dart
      <功能名稱>_state.dart
      <功能名稱>_controller.dart
      widgets/
  shared/
    widgets/
    theme/
    utils/
```

- `main.dart` 僅處理應用程式啟動與必要初始化。
- `app.dart` 集中處理 `MaterialApp`、主題與路由的組裝。
- 功能頁面應保留畫面組裝；商業規則、資料轉換與長流程應移至同功能下可測試的類別。
- 共用程式碼只有在至少兩個功能真正共用後才移入 `shared/`。
- 若專案已有既定結構，必須優先遵循既有慣例，不強制套用本範本。

## 介面與可近用性

- 先遵循既有設計系統、顏色、字型與間距，不自行引入另一套視覺風格。
- 對高齡使用者、照顧者或資訊密集流程，優先考慮清楚文字、足夠點擊區域、明確狀態與可理解的錯誤訊息。
- 不只用顏色傳達成功、失敗、警示或選取狀態；應搭配文字、圖示或其他可辨識訊號。
- 表單需顯示輸入規則、即時但不打斷操作的驗證訊息，以及可復原的錯誤處理。
- 儲存、刪除、同步與匯出等有狀態變更的操作，必須提供進行中、成功與失敗回饋。
- 對不可逆或高影響操作，先明確說明影響並要求確認。

## 資料、隱私與安全

- 不硬編碼 API key、密碼、權杖、使用者識別資料或健康資料。
- 只蒐集、讀取與保存完成需求所必需的資料。
- 對照片、健康資料、通知與檔案存取，於真正需要功能時才請求權限，並向使用者說明用途。
- 不記錄敏感內容到 console、分析服務或可被他人讀取的錯誤訊息。
- 對外部輸入、深層連結、檔案與資料庫內容都要驗證格式與範圍。
- 未經明確需求，不得將本機資料上傳、同步或分享至外部服務。

## 程式碼品質

- 使用 Dart 慣例命名：檔名使用 `snake_case`，類別使用 `PascalCase`，變數與方法使用 `camelCase`。
- 優先使用 `const` 建構子與不可變資料；只有需要時才使用可變狀態。
- Widget 保持聚焦。當一個 `build` 方法難以閱讀或重複出現時，再拆出具名稱的小 Widget。
- 註解解釋為何採取某個做法，不逐行重述程式本身。
- 錯誤訊息、空狀態與日誌須使用繁體中文，並提供使用者可採取的下一步。
- 不用全域可變狀態作為跨功能捷徑；先確認狀態的生命週期與擁有者。

## 驗證流程

每次程式變更後，依影響範圍執行下列檢查：

1. 執行 `dart format` 格式化受影響的 Dart 檔案。
2. 執行 `flutter analyze`，不得新增分析錯誤或未解決警告。
3. 執行相關 `flutter test`；修改資料處理或狀態邏輯時，優先補上單元測試。
4. 修改 Widget、表單、載入或錯誤狀態時，補上或更新 Widget 測試。
5. 實機或模擬器驗證只用於使用者可見流程，至少涵蓋正常、空資料、載入、失敗與重試情境。
6. 最後執行 `git diff --check`，確認沒有空白字元或換行問題。

若因環境、SDK、模擬器或相依問題無法驗證，需明確報告未執行的命令、失敗原因與使用者可採取的下一步。

## 變更與版本控制

- 只修改與本次需求直接相關的檔案。
- 不執行 `git reset --hard`、`git checkout --`、遞迴刪除或其他難以復原的操作，除非使用者明確要求。
- Commit message 使用繁體中文，描述使用者可感知的變更，例如：`新增每日飲水紀錄`。
- 建立分支時預設使用 `codex/` 前綴，除非使用者指定其他命名。
- 未經使用者要求，不得自行推送、建立 Pull Request、發布套件或修改正式環境設定。

## 回覆格式

完成工作時，回覆應包含：

1. 狀態：完成、部分完成或受阻。
2. 修改內容：以使用者可理解的方式列出關鍵檔案與行為。
3. 驗證：列出已執行命令與結果；未執行的驗證需說明原因。
4. 風險或待確認事項：只列出會影響下一步決策的內容。
