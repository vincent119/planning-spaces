# Group Based Operation Permission Requirements

## Introduction

目前部分功能操作同時受到群組管理權限、全域角色與 `project_members` 專案角色影響。這會讓已在群組管理中授權的使用者，因為沒有被加入某個專案成員而收到 `403`，也會造成前端選單與後端授權判斷不一致。

此行為與目標權限模型不一致。系統所有功能的讀取、建立、修改、刪除，都應依照「群組管理」中的表單節點權限作為主要控制來源。若使用者沒有某個表單節點的 `read` 權限，前端不應顯示該表單、頁面、選單或入口。

`project_members` 僅作為專案成員資料與專案關聯資訊，不應參與一般功能操作授權。專案成員不參與 Ticket 建立修改、Jira 匯入，也不應成為其他功能操作能否執行的前置條件，除非該功能未來有明確規格定義為「專案成員管理」本身。

## Requirements

### 需求 1：所有功能操作以群組權限為準

**使用者故事**：身為系統管理員，我希望所有功能的讀取、建立、修改、刪除都依照群組管理設定控制，讓 UI 顯示與 API 授權維持一致。

#### 驗收條件

- [ ] 1.1 所有 API 操作應先依照群組管理對應表單節點與 action 判斷權限。
- [ ] 1.2 `read` 權限控制資料讀取、頁面可見性、選單入口與表單入口。
- [ ] 1.3 `create` 權限控制新增與匯入類操作。
- [ ] 1.4 `update` 權限控制編輯、狀態變更、重新整理草稿、指派與其他修改類操作。
- [ ] 1.5 `delete` 權限控制刪除類操作。
- [ ] 1.6 `admin` 維持既有最高權限。
- [ ] 1.7 未具備群組管理對應權限的使用者，後端應回 `403`。
- [ ] 1.8 `system/logs` 屬於可讀取授權節點；使用者具備 `system/logs read` 時可查看日誌查詢頁，不需 `admin` 全域角色。

### 需求 2：沒有讀取權限時前端不可見

**使用者故事**：身為一般使用者，我只希望看到自己有權限使用的功能，不要看到點進去才被拒絕的頁面或表單。

#### 驗收條件

- [ ] 2.1 使用者沒有某表單節點 `read` 權限時，左側選單不得顯示該入口。
- [ ] 2.2 使用者沒有某表單節點 `read` 權限時，直接輸入 URL 進入該頁面應顯示無權限頁或被導回可用頁面。
- [ ] 2.3 使用者沒有父節點 `read` 權限，且沒有任何可讀子節點時，父節點選單不得顯示。
- [ ] 2.4 使用者有可讀子節點時，父節點可作為展開容器顯示，但不得讓使用者進入沒有 `read` 權限的父頁面。
- [ ] 2.5 表單內的新增、編輯、刪除、匯入、匯出、確認、重新整理等操作按鈕，應依照對應 action 權限顯示、停用或隱藏。

### 需求 3：專案成員不參與一般功能操作授權

**使用者故事**：身為系統維運者，我希望專案成員資料只表達專案關聯與專案成員管理用途，不再被混用為一般功能操作權限來源。

#### 驗收條件

- [ ] 3.1 `project_members` 不得作為 Ticket 建立、Ticket 修改、Jira 匯入、報表操作、排班操作或系統一般功能操作的必要條件。
- [ ] 3.2 專案成員維護功能本身仍可保留既有管理權限限制。
- [ ] 3.3 值班人員、指派人員與排班人員的選項來源不得依賴使用者是否為某專案成員。
- [ ] 3.4 若 API 仍需要 `project_id`，該欄位只作為資料歸屬、查詢條件、資料隔離條件或報表維度，不作為操作授權條件。
- [ ] 3.5 若某功能確實需要專案成員角色作為業務規則，必須另開規格明確定義，不得隱含在共用 middleware 中。
- [ ] 3.6 `/api/v1/projects` 專案清單不得因使用者未存在於 `project_members` 而回傳空清單；專案入口可見性應依使用者是否具備任一專案工作區表單 `read` 權限判斷。
- [ ] 3.7 `projects.visibility = private` 表示專案資料可見性語意，不得被隱性解讀為必須加入 `project_members` 才能看到專案入口；若未來需要私有專案資料隔離規則，必須另開規格定義。

### 需求 4：前後端權限契約一致

**使用者故事**：身為前端工程師，我希望後端提供穩定的權限契約，讓前端能依照同一份權限資料決定選單、頁面與操作按鈕狀態。

#### 驗收條件

- [ ] 4.1 後端應提供目前登入者可用的表單節點與 action 權限資料。
- [ ] 4.2 前端選單與頁面入口應以後端權限契約為準，不得在前端硬編角色判斷。
- [ ] 4.3 前端操作按鈕應以後端權限契約為準，不得以 `global_role` 單獨判斷。
- [ ] 4.4 後端 API 仍必須執行同等權限檢查，不得只依賴前端隱藏按鈕。
- [ ] 4.5 若既有 `/api/v1/admin/*` API 必須維持 `admin` 專用，需為可授權節點提供非 admin path 的等價讀取 API，避免前端有入口但 API 固定 `403`。

### 需求 5：授權失敗原因可診斷

**使用者故事**：身為維運者，我希望當操作被拒絕時，可以分辨是群組權限不足、資料不存在、或請求參數錯誤，而不是誤判為專案成員不足。

#### 驗收條件

- [ ] 5.1 操作被拒時，後端測試或 log 應能分辨為群組權限不足。
- [ ] 5.2 讀取被拒時，前端應能呈現一致的無權限狀態。
- [ ] 5.3 移除或停用專案角色檢查後，相關測試不得再期待 `project_members` 缺失造成 `403`。
