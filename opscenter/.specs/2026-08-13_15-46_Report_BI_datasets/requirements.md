# Report BI 資料集需求

## 文件定位

本規格規劃 Report 的 BI 資料集層，接續既有 Report V2 自訂查詢與 V3 多區塊範本能力。既有 Report 規格、固定月報與範本契約均維持不變；本規格未經使用者安排前不得開始程式實作。

## 背景

目前報表設計器雖已有多區塊、畫布、共用參數與版面配置，但可選資料集主要是 Ticket 運維事件。報表作者仍需受限於單一資料視角，難以在同一份營運報表中組合人員工作量、值班執行與主專案總覽。資料集層需要提供可治理的業務欄位、固定指標口徑與權限邊界。

## 目標

- 提供多個由後端治理的資料集，供 BI 範本的 KPI、圖表與表格區塊使用。
- 以維度、數值、篩選器與視覺化 metadata 取代前端硬編碼選項。
- 讓固定 OP 指標、Ticket 統計與值班統計在所有報表中的數字一致。
- 保持既有 V1、V2、V3 範本及固定模式 A 至 G 的相容性。

## 非目標

- 不開放使用者輸入 SQL、JavaScript、HTML、任意公式或跨資料集 join。
- 不在第一階段建立資料倉儲、OLAP cube、即時串流分析或自由建立資料集的管理介面。
- 不改寫既有固定月報、值班統計、Jira 匯入、SLA 或既有範本的統計結果。

## 第一階段資料集

| 代碼 | 名稱 | 用途 | 初始資料來源 |
| --- | --- | --- | --- |
| `ticket_events` | Ticket 運維事件 | 分析 Ticket、來源、專案、人員、班別與狀態 | `tickets` 與既有關聯主檔 |
| `shift_execution` | 值班執行統計 | 分析每日／班別／人員的 Ticket 總量、處理進度、固定 OP 指標及告警／域名處理量 | Ticket、班別與既有值班聚合 |
| `person_workload` | 人員工作量 | 比較人員、班別、專案與期間工作量及處理進度 | Ticket、活動與班別資料 |
| `project_operations` | 主專案營運總覽 | 彙總主專案開單、未結案與固定 OP 指標 | Ticket、專案與 OP 指標聚合 |

Jira 執行統計與 SLA 績效列為第二階段，需待其來源資料與指標口徑完成後另立規格。

## 資料集契約

每個資料集必須定義：

- 代碼、顯示名稱、說明、版本與啟用狀態。
- 維度：代碼、名稱、型別、可否分組、篩選、排序及日期粒度能力。
- 數值：代碼、名稱、聚合方式、去重鍵、日期欄位、狀態口徑及支援的區塊類型。
- 篩選器：可用運算子、選項來源及可否繫結共用參數。
- 支援的視覺化類型與資料列、分類、系列上限。
- Report 權限、專案範圍、資料可見性及敏感欄位遮罩規則。

metadata 不得回傳 SQL、內部欄位名稱、資料庫連線資訊、未授權專案名稱或敏感資料。

## 指標治理

- 指標由後端版本化定義；範本只保存指標代碼，不保存 predicate、SQL 或公式文字。
- `op_jira_issue_count` 以 `tickets.external_ref` 去除前後空白後非空計數。
- `op_alert_notification_count` 以 `ticket_resources.resource_type = alert` 計數。
- `op_payment_domain_change_count` 以 `ticket_resources.code = business_domain_change` 計數。
- 同一指標在 KPI、圖表、表格、固定月報與 CSV 中必須使用相同口徑；前端不得重算核心數字。

## 效能與彙總來源策略

資料集是語意契約，不與單一資料庫 table、view 或 materialized view 綁定。後端可依查詢類型使用原始資料表、一般 view、materialized view 或預聚合表；範本及前端只使用資料集代碼、維度與數值代碼，不得感知或指定實體來源。

- 一般 view 僅用於封裝可重用關聯或統計口徑，不得宣稱可自動改善查詢效能。
- materialized view 或預聚合表只用於已量測為高頻且固定粒度的彙總，並須明確定義刷新策略與資料新鮮度。
- 即時明細、任意日期區間、臨時篩選與可下鑽 Ticket 資料優先讀取原始資料表及適當索引，避免因彙總資料失去篩選能力或即時性。
- `ticket_events` 初期以原始 Ticket 查詢及索引優化為主；`shift_execution` 視高頻每日統計需求評估日聚合表；`person_workload` 評估日／月彙總；`project_operations` 優先評估主專案月度 materialized view。
- 任何彙總來源導入前，必須量測原始查詢基準、確認更新時效需求，並驗證其結果與原始資料查詢口徑一致。
- materialized view／預聚合表的刷新失敗、延遲或資料過舊時，介面需能顯示資料更新時間與明確狀態，不得靜默回傳過時結果。
- 實體彙總來源的 schema、索引、權限與刷新排程必須使用 migration／部署流程管理，並具備回滾與重建程序。

## 範本與權限

- V3 的每個資料區塊選擇一個資料集，且只能使用該資料集公開的欄位與視覺化。
- 同一份 V3 範本可使用多個資料集；每個區塊仍須獨立通過 Report 權限、專案與子專案範圍驗證。
- 第一階段共用參數至少支援日期區間與子專案，並預留主專案、人員、班別、事件類型、資訊來源、狀態與優先級。
- 第一階段資料集由系統開發及版本控制維護；一般使用者不可自訂資料集或指標。
- 建立、修改、發布範本沿用 Report `create`／`update` 或 Project Manager 權限；一般成員只能執行可見且已發布的範本。
- `project_operations` 的範圍為使用者具 Report `read` 權限且可見的全部主專案；報表提供主專案下拉複選篩選，不得回傳或統計未授權主專案。
- `person_workload` 同時提供開單人員、指派人員與活動操作人員三種明確的人員口徑；每一個數值必須標示所使用的口徑與 Ticket／活動去重規則。
- `shift_execution` 除既有每日矩陣外，同時支援適用的長條圖、折線圖與表格；各呈現方式必須共用同一後端統計口徑。
- BI 範本具草稿與已發布狀態；草稿只有建立者、具範本管理權限者可查看及執行，一般成員只能查看與執行已發布且可見的範本。

## 驗收條件

- [ ] 提供資料集列表與 metadata，前端只依 metadata 顯示可選維度、數值、篩選器與視覺化。
- [ ] 第一階段提供四個資料集，且均有名稱、說明、欄位、權限與資料量限制。
- [ ] 未知資料集、維度、數值、運算子、排序欄位或視覺化類型由後端拒絕，不得產生動態 SQL。
- [ ] V3 範本可在不同區塊使用不同已授權資料集，保留獨立 loading、empty、error 與局部重新查詢。
- [ ] 日期區間與子專案可作為共用參數，其他規劃參數具可擴充與可繫結契約。
- [ ] 固定 OP 指標在所有資料集呈現與匯出中保持一致，並有正向及反向測試。
- [ ] 既有 V1、V2、V3 範本與固定模式 A 至 G 可持續讀取、預覽、執行及匯出，數字不變。
- [ ] 每個首批資料集至少提供一個系統範例範本或快速建立起點，涵蓋 KPI、圖表與明細表。
- [ ] 導入任何 view、materialized view 或預聚合表前，均完成慢查詢基準、索引檢查、資料新鮮度、刷新失敗處理及與原始查詢一致性的驗證。

## 待確認決策

已確認：BI 範本區分草稿與已發布；主專案營運總覽可跨使用者可見主專案並提供下拉複選；人員工作量同時支援開單人員、指派人員及活動操作人員；值班執行統計同時支援矩陣、長條圖、折線圖及表格。
